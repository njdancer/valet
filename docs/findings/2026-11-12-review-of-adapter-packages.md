# B's review of C's adapter-packages.md (hash, storage, install, rollback)

Reviewed: docs/adapter-packages.md on claude/project-thread-2jze1m, 2026-11-12. The hash formula and coverage, no cached compile output, names on disk, and load-time re-hashing are good. Fold these in, most important first.

1. **Blocker: describe runs unapproved code.** Until workstream I lands, the tool process is a full Node process (node:vm is not a boundary). So "compile and describe" at install runs whatever a package contains, with Valet's own access, before anyone approves it. That is acceptable for built-ins and dev-build folders. It is not acceptable for drafts written by an agent that a page may have prompt-injected. Rule: the `draft` source must not run describe, or any other non-built-in code, until I's sandbox exists. F's draft tests and live trials fall under the same rule. Write it into the doc and leave a guard in `install` that refuses `draft` with a clear reason, so F can't wire it up by accident. Until then, B's approval cards mark every non-built-in adapter as running unsandboxed: critical, and approvable only at the Mac.

2. **The approval store decides what runs, not state.json.** State the invariant that an adapter has at most one approved hash. `ApprovalStore.approve` already replaces the earlier one. Pin it with a test: activating a stored but unapproved hash shows no tools. With that invariant, editing `active` in state.json gets an attacker nothing, so state.json needs no integrity protection. The tamper paragraph can then say that approvals and grants become trusted stores under B: signed evidence on each record, plus a hash anchor in the Keychain (core `trusted-store.ts`; D builds it). Once D builds that, "someone who can write approvals.json" stops being a gap.

3. **Rollback can widen permissions without saying so.** An older version may have more egress, requests or secrets than the active one. The Roll back confirmation should show the target's permission diff against the active version, not just "Roll back". Revived grants must be exactly the ones still in the grant store for that hash: a secret the person revoked after moving off that version stays revoked. Test that. Once D lands, rollback becomes an `adapter-install` approval request. The one-click Mac gesture is fine until then.

4. **The same id inherits the signed-in session.** Partitions are named by adapter id, so a draft or folder package with id `woolworths` gets Nick's logged-in Woolworths cookies once it is approved. J5 (repair) needs exactly that, but the approval must say so. When an install replaces an adapter that has a live session or grants, the permission diff gets a high-risk line: "This code will use your signed-in session for <site>". The card must also show the source as replacing the built-in; today it would read like an ordinary update.

5. **Record what the hash doesn't cover.** Put the app version, the library prelude's hash and the esbuild version in each version's state entry and in `adapter-installed`. An app update that changes what an approved hash runs then shows up in the history. It is small, and it closes the gap your doc names.

6. **Minor: schemas from describe.** Besides the byte and depth limits, cap the node count, and accept only the JSON Schema keywords that zod's toJSONSchema actually emits (refuse unknown ones). That keeps `fromJSONSchema` in the main process on a known path.
