siteadapter mockups
Static HTML. Woolworths is the worked example. 7 Nov 2026.

A menu-bar app that runs per-site adapters and exposes their tools over MCP. Adapter code never sees a secret: logins happen in a separate browser session, filled from 1Password, and every request a tool makes is checked against what its manifest declared. Each screen below shows one part of that model.

Choices these mockups make that need your call

  • Touch ID on irreversible confirmations The “Place order” button asks for Touch ID. Without it, anyone at the unlocked Mac can approve. Default here: on.
  • Carrying a grant across an update A new hash starts with no grants. The review offers to re-bind the same item and origins only when the login steps, navigation and that secret's origins are identical in both versions, and the box starts unticked. The 0.4.0 example changes login, so it isn't offered. Or should every update need a fresh grant?
  • A token per client Each client gets its own token from “Connect a client…”, with its own Rotate and Revoke, and calls are attributed to the token. Today there is one shared token, so the client name in the audit log is whatever the client says it is. Per-token “Read only” or “All tools” scopes are drawn as a proposal.
  • Remote access Drawn as a proposal, not in v0. Is it in v0 at all? If so, which tools may a remote caller use (proposed: read only), with a separate token per device? The security model needs a section on it before it ships.
  • needsUser ends the call Drawn the way core records it: the call returns needsUser, the login window stays open, and the agent calls again once you're signed in. Pausing the call instead would need a core change.
  • Confirmation timeout Unanswered confirmations time out after 2 minutes and the client is told “timed-out”, which core keeps distinct from “declined”. Login windows close after 5.
  • What the confirmation can vouch for The order total and card come from the adapter and are tagged “Not verified by siteadapter”. A one-shot unlock of PlaceOrder for that call, and a total siteadapter saw itself, are drawn as proposals.
  • Requests per tool Adapter detail shows the calls each tool typically makes, from recent runs. The manifest gives every tool the whole request surface, so a read tool's code may call a declared write path. Binding requests to tools needs core.
  • “Filled by siteadapter” The hand-off window lists the filled fields in the app's own banner, outside the web view. There are no badges inside the page: anything drawn there, the site could imitate.
  • SMS codes A Messages code source is declared by the manifest alone, with no grant step, so the screens show it as a declared permission, not under a grant. Should reading codes need a grant, with the sender required?
  • Rate budget and cool-down numbers 60 requests an hour for Woolworths, and a 1-minute cool-down that doubles on repeat blocks. Placeholders until we measure.
  • Login origins https://auth.woolworths.com.au is a stand-in second origin to show granting a subset. The real login flow still has to be recorded with you present.
  • Approval friction Approve is enabled only after ticking “I've read the highlighted additions”, and only when an update adds something.

Open questions for you

  1. May an update re-bind an existing grant (unticked, only when login is unchanged), or does every update need a fresh grant?
  2. When a login needs you, should the tool call end with needsUser (as core has it) or wait for you?
  3. Is remote access in v0? If yes: which tools, and one token per device?
  4. Are per-client scopes worth building in v0, or are per-client tokens with Revoke enough?
  5. Should reading an SMS code from Messages need its own grant?
  6. Touch ID on irreversible confirmations: on by default?

Core changes these screens assume

Nothing below exists in packages/core yet. Each is drawn on a screen as a proposal.

  1. Client registry keyed by token. Issue one token per client; tool-called.client is the token's id, and the client's self-reported name is stored separately. Optional per-token tool scopes.
  2. Grant events say what was granted. grant-made and grant-revoked carry adapterHash, origins and the provider (never the item reference), plus carriedFrom if re-binding is accepted. adapter-approved carries the version.
  3. A grant for a Messages code source, with the sender required and the origins the code may be filled on.
  4. Confirmation-scoped unlock. Approving allows one irreversible request, bound to the callId, consumed on use and audited. Optionally record a runtime-observed total from a declared GET as a checked fact.
  5. Per-tool request binding: tools[].requests, with decideRequest also checking the calling tool and its side effect.
  6. Where assertLoggedIn runs. The probe is documented as running in the tool partition; the trace shows it after the hand-off. Core should say so for the auth step too.
  7. Anchoring the audit log so truncating the tail or rewriting the whole chain is detectable, e.g. by periodically recording the head hash somewhere the app can't rewrite.
  8. If needsUser should pause the call, a non-terminal event for it; today it's a terminal outcome of tool-finished and login-finished.
