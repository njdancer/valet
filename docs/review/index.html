Try it

Everything runs against the local fake; no real account, 1Password, Keychain or Messages is touched.

  1. mise install && pnpm install
  2. pnpm demo builds the demo and launches the menu-bar app (a DEMO badge in the menu bar). It serves the fake on www.woolworths.test and auth.woolworths.test over TLS, inside the app.
  3. In the control panel: approve Woolworths, grant login from “Woolworths (demo account)” and Messages codes from Woolworths.
  4. Settings → Clients: copy the snippet into Claude Code's MCP config (server siteadapter-demo).
  5. Ask Claude Code to search for milk (no login), then add some to the cart. The first cart tool logs in through the hidden auth window; open the run trace to see each fill and its checks. Calls are spaced 10 s apart, as they will be on the real site.

Checks: pnpm check (lint, both typechecks, tests with coverage), pnpm test:e2e (the desktop suite, about 5 minutes), pnpm package:smoke (an unsigned .app, launched under a temporary HOME).

Known gaps and risks

  • Nothing live while logged in: spike 1, the Auth0 password and MFA pages, the silent re-login, the login probe and the checkout paths all need you at the keyboard.
  • The automated login inside a call isn't paced or watched for block pages yet (D55); the app's own login steps are.
  • A cancelled call's login runs on to its own deadline and can leave the attempt marker set (D67).
  • The stdio bridge is refused in a packaged build until D60; the update feed has no signing key until D61.
  • Tool code runs in the main process behind the guarded page, not in a separate process yet (M3; sandbox in M7).
  • Never exercised for real: 1Password, the Keychain prompt, Full Disk Access, a Developer ID signature, notarisation, an x64 build.
  • Fixed tonight: the Woolworths adapter spaced calls 2.5 s apart, the pace Akamai blocked in the live probe. It's now 10 s.
  • Small UI gaps: the tray counts sessions but says clients (D68); the tray icon is generic; the run trace shows only the blocked count.

Sandbox technology

Blocks M7

Recommendation. Spike the sandboxed renderer and QuickJS-wasm against the hostile-adapter suite in M7, and pick on evidence. Lean towards the sandboxed renderer: tool code is mostly orchestration of capability calls, so its speed doesn't matter, and it adds no dependency.

Options and reasoning
  • Options:
    • QuickJS compiled to wasm (e.g. quickjs-emscripten): a strong boundary with nothing reachable but what's injected; slower, and tool code can't use Node or modern-JS features QuickJS lacks; a new dependency.
    • isolated-vm: a V8 isolate in-process; fast; a native addon (rebuild per Electron), and its README described the project as in maintenance mode at last check; verify before choosing.
    • A sandboxed hidden renderer: tool code runs in a BrowserWindow with sandbox: true, no Node, a partition whose webRequest blocks everything, and the capability API over a MessagePort. Chromium's renderer sandbox is battle-tested, and it costs no dependency. Heavier per run (a renderer process).
    • SES / Hardened JS compartments: good capability discipline, but same process and realm; not a boundary on its own.
  • Recommendation: spike the sandboxed renderer and QuickJS-wasm against the hostile-adapter suite in M7, and pick on evidence. Lean towards the sandboxed renderer: tool code is mostly orchestration of capability calls, so its speed doesn't matter, and it adds no dependency.

Rate budget defaults

Answer first Blocks M2

Recommendation. Start here and loosen only with evidence from M2 and M3, never the other way round. A test asserts the run 1 pattern can't get through the defaults unspaced.

Options and reasoning
  • Known-bad baseline. Run 1 of the live probe loaded the homepage and then made 4 scripted API calls about 2.5 s apart, with no navigation in between. That was enough for Akamai to flag the UA from Nick's IP within three minutes (finding). Every default must be clearly less aggressive than that, on every axis.
  • Starting defaults for Woolworths:
    • Minimum gap of 10 s between direct API calls (page.fetch and the probe), with upward-only jitter of 0–50% (so 10–15 s, never less than 10). Four times run 1's gap.
    • At most 2 direct API calls per page view. After two, the next one waits for a real navigation (the runtime navigates to a relevant page, such as the trolley or a search URL) as well as the gap. Run 1 made 4 with none.
    • At most 4 direct API calls a minute, and 60 an hour.
    • Prefer page-initiated reads. Navigating to a search URL and reading the response the page fetched itself counts as a navigation, not a direct call.
    • Cache reads for the session: search and product detail until the session ends; the trolley until any write, after which the write's own response is the new cached trolley.
    • Cool-down: 30 minutes after any block, doubling up to 6 hours on repeat blocks, persisted across restarts. No call reaches the site during it.
  • A realistic weekly shop (about 30 tool calls, many served from cache) then takes roughly 15–30 minutes. That's slow for a bot and fine for an agent doing a shop in the background.
  • Where the code is. Round 1's runtime has the minimum gap and the cool-down only, with looser defaults (2 s; 10 minutes doubling to 2 hours, which are also core v2's limits defaults), in memory, with no jitter, no per-page-view or per-minute cap, and no read cache. Reconciling the two is D33.
  • What it covers. The budget and breaker sit in the runtime's guarded page and probe, so they see page.fetch, goto and the probe only.   • Why it matters: run 1's block came from a burst of requests. AC7 fails if anything bypasses the budget, and AC9 says no call reaches the site during a cool-down. Neither can pass.
  • Options: leave it (tools must use page.fetch and goto; reviewers reject adapters that don't); move the budget into the driver entirely; split it: the runtime keeps the budget and breaker, the driver reports to them and asks them.
  • Considerations: the driver sees every request in both partitions with its resource type and status, so it is the only place that can spot a block page served to a page-initiated request or a login. But pacing every subresource would break pages; only main-frame navigations are worth spacing, and the site's own XHRs follow from them. Keeping the state in the runtime keeps one breaker per host whichever partition saw the block.
  • Recommendation: split it (C16). The driver reports block signatures (a 403 HTML page, Akamai's "Access Denied … Reference #" page, a 429) on navigations and API calls in both partitions to the runtime's breaker, and waits on the runtime's budget before each main-frame navigation, tool- or page-initiated, in both partitions. An open breaker cancels every request to that host in the tool partition and ends a login as blocked. AC7's test then counts requests at the fake site, not at the capability API.
D56

URL regex deadline

Blocks M7 (third-party adapters). Nothing for Woolworths, whose flow needs only urlContains

Recommendation. The worker with a deadline (C19), shared with the OTP matcher, and the input bound lowered to 256 as well. Until then, reject urlRegex in third-party manifests, and prefer urlContains in first-party ones.

Options and reasoning
  • Today: urlRegex conditions run synchronously in the main process. On main the auth flow compiles and runs them with a 2,048-character bound on the path and query, no screen and no deadline. Core v2 adds the parse-time screen, which stops exponential shapes but not polynomial ones such as \d*\d*\d*\d*x: at 2,048 characters a degree-4 pattern needs on the order of 10^13 steps. A hostile adapter controls the pattern, and through goto(url) to its own navigation origins, the input too. That freezes the trusted main process: logins, the MCP endpoint and the audit log. OTP patterns already run in a worker under a deadline.
  • Options: run urlRegex in the same worker-with-deadline as OTP patterns, a timeout counting as "doesn't match"; cap quantifiers per pattern (say at most two unbounded ones) and lower the input bound to about 256 characters; drop urlRegex and keep only urlContains.
  • Considerations: waitFor polls its condition, so a worker round trip per poll costs latency, but conditions are polled every few hundred milliseconds at most, and a worker can be kept for the length of a login. A quantifier cap is cheap but is another screen that a cleverer shape might pass. Most real login flows only need urlContains.
  • Recommendation: the worker with a deadline (C19), shared with the OTP matcher, and the input bound lowered to 256 as well. Until then, reject urlRegex in third-party manifests, and prefer urlContains in first-party ones.

Options and reasoning

Page-initiated traffic

Answer first Blocks M2. Until it's decided, the current Woolworths manifest breaks under the v2 policy

Recommendation. Two ceilings (C17); host on declarations, defaulting to the home host, with the site's own non-GET background calls declared on their real hosts under a telemetry purpose that ranks with read and that no tool can call through page.fetch; and deny segments limited to R17's resource types. Options and reasoning

G1's own warning (keep the partition-wide ceiling apart from the page.fetch count) was lost when core v2 merged them. Cancelling a site's own sensor traffic is the kind of difference from the person's own browser D24 tells us to avoid.
  • Recommendation: two ceilings (C17); host on declarations, defaulting to the home host, with the site's own non-GET background calls declared on their real hosts under a telemetry purpose that ranks with read and that no tool can call through page.fetch; and deny segments limited to R17's resource types. D60

The stdio bridge in a packaged app

Answer first Blocks M3 (onboarding, AC3)

Recommendation. A small Swift proxy in Contents/MacOS/, signed with the app and covered by its designated requirement. Snippets point at its absolute path in the installed app.

Options and reasoning
  • Today: client snippets start the bridge with tsx from the repo, which needs Node 24 on PATH. A packaged build has no bridge command and shows no snippets. The RunAsNode fuse is off, so the app's own Electron binary can't run the bridge as Node.
  • Options: a tiny separate binary in the app bundle (a Node single-executable app, or a small Swift or Go stdio-to-HTTP proxy), signed with the app; a second, unfused helper Electron binary; tell people to install Node and run npx.

A second Electron binary doubles the bundle and brings back the fuse problem. npx asks every user to install Node and trusts a registry at every start.
  • Recommendation: a small Swift proxy in Contents/MacOS/, signed with the app and covered by its designated requirement. Snippets point at its absolute path in the installed app.

What the auth probe can't hide

Recommendation. Keep net.request and measure in M2's live session. Move to a page-world fetch only if Akamai reacts to the probe.

Options and reasoning
